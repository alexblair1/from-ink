# From Ink — Localization Engineering Design

> **Status:** Draft. The "Target Languages" list (§3) is **TBD** — the project ships with the intent of "8 languages and 130 countries" but the specific eight have not been ratified. The rest of this document defines the architecture that the eight will plug into; the architecture stands whether the list is 8 or 8+N.

---

## 1. Goals

- Every user-facing string the team writes is translatable. Strings the user authored (event titles, notebook names) pass through verbatim.
- Every feature that uses Apple Foundation Models gracefully hides its FM-generated surface when the model is unavailable or the user's locale is unsupported, without faking output. Apple Intelligence availability is **never** a correctness dependency, and the team does not hand-author mechanical fallback prose in multiple languages — that buys nothing the underlying data surfaces don't already give the user. See §5 for the hide-rather-than-fake rule.
- Date, time, number, and list formatting always honor the user's locale via a single canonical source (`CalendarContext`). No bare `Date()`, `Locale.current`, or hard-coded separators.
- Right-to-left layout direction, non-Latin numbering systems, and non-Gregorian calendars are first-class. The architecture handles them; individual features do not.
- A feature whose quality cannot be guaranteed in the user's locale is **gated** — disabled, degraded, or hidden according to the policy in §6. The user never sees a broken or English-mixed surface as a fallback.

## 2. Glossary

| Term | Meaning |
|---|---|
| **Target language** | One of the (8, TBD) languages the team commits to shipping translated strings for. See §3. |
| **Supported locale** | A `Locale` that maps to a target language and whose region/script we explicitly handle (e.g., `pt_BR` and `pt_PT` may both be supported, or only one). |
| **FM-supported language** | A language Apple Foundation Models can produce output in. See §4. |
| **FM-gated feature** | A feature whose primary content is generated by Foundation Models. Examples today: Daily Brief focus/suggestion text. Future: handwriting task extraction, page summaries. |
| **Deterministic fallback** | The non-FM code path that produces the same kind of content from the same inputs without invoking a language model. Must exist for every FM-gated feature per §5. |
| **Authored content** | Strings the user typed: event titles from EventKit, reminder titles, notebook names, page text. Pass through unchanged; never translated. |
| **Chrome** | Strings the team wrote: button labels, section headers, empty states, fallback prose, accessibility hints. Always localized via `AppStrings`. |

None of these are FM-supported. The list should be confirmed with that constraint in mind.

## 4. Apple Foundation Models language coverage

This section is **time-sensitive** — Apple expands coverage with iOS updates. Verify against [Apple's supported languages and locales documentation](https://developer.apple.com/documentation/foundationmodels/supporting-languages-and-locales-with-foundation-models) before relying on it.

**Live as of iOS 26 launch (Sept 2025) — 9 languages:**

English, French, German, Italian, Portuguese (Brazil), Spanish, Chinese (Simplified), Japanese, Korean.

**Announced "coming soon" — 8 additional:**

Danish, Dutch, Norwegian, Portuguese (Portugal), Swedish, Turkish, Chinese (Traditional), Vietnamese.

**Not on either list** (representative — not exhaustive):

Arabic, Hebrew, Persian, Urdu, Hindi, Thai, Bengali, Tamil, Greek, Polish, Hungarian, Czech, Romanian, Catalan, Finnish, Russian, Indonesian, Filipino, and most African and Indigenous languages.

**Implication for From Ink:** If any target language is not FM-supported, users in that language receive the deterministic fallback (§5) for every FM-gated feature, indefinitely. The fallback is not a degraded experience for those users — it is *the* experience. This makes fallback quality load-bearing.

**Runtime checks the framework provides:**

```swift
SystemLanguageModel.default.isAvailable                        // device-level
SystemLanguageModel.default.supportedLanguages                  // Set<Locale.Language>
```

Used in `FoundationModelsService.supportsLocale(_:)` to gate FM calls. See `DailyBriefClient._runGeneration` for the canonical pattern.

## 5. The hide-rather-than-fake rule

> **When an FM-gated feature wraps or comments on data that the user can see elsewhere in the UI, and FM cannot produce its output in the user's language, the feature hides rather than synthesizes a fallback.**

The rationale: hand-authoring N-language localized prose that mechanically restates data the user already sees costs significant translation budget and adds zero value over the data itself. The user has not lost information — they still see the underlying data through whatever surface presents it directly. The editorial layer simply does not appear.

This rule has four concrete consequences:

1. **No mechanical fallback prose.** Code that strings together "You have %@ at %@, %@ at %@…" sentences is a localization tax with no payoff. Don't ship it. The user's tab strip / list / detail view already shows what the prose would have restated.
2. **The view layer is responsible for hiding the FM-empty surface gracefully.** Empty `focusText` (or equivalent) signals the view to omit the section entirely; the surrounding chrome reflows naturally.
3. **The feature's worth is FM's editorial judgment, not its access to data.** If FM can't produce the editorial layer, the feature isn't broken — it's just absent for that user / locale / session. The underlying data presentation is unaffected.
4. **The rule applies when there's a meaningful data surface elsewhere.** A feature whose data is *only* available through the FM-generated output (with no separate tab or list view) doesn't get this dispensation — it must use the gating policy in §6 to disable or hide.

**Canonical example.** Daily Brief's editor's note hides entirely when Foundation Models is unavailable, the user's locale is unsupported, or FM retries are exhausted. The Calendar / Reminders / Birthdays tabs below continue showing the same events and reminders directly. The user has lost nothing they didn't already have. See `DailyBriefClient._runGeneration` and `HomeDailyBrief.Model.init` (the `showsEditorsNote` resolution).

**What this replaces.** A previous draft of this rule required maintaining a hand-written `rawFocusFallback` function in five `AppStrings` keys, translated per target language. Removed once it became clear that the fallback prose carried no information beyond what the tab strip already shows. Localizing it would have meant ~40 translation cells (5 keys × 8 languages) of restated data. The hide-rather-than-fake rule is the principled reason that work was the wrong shape.

## 6. Feature gating policy

Three options when a feature cannot produce quality output in the user's locale. Pick the right one based on the feature's role.

### 6.1 Hide the FM-generated surface (default for data-wrapper features)

The FM-generated surface omits itself; the underlying data presentation continues unchanged. The user has not lost information — they still see the data through its dedicated UI surface (tab, list, detail view). The editorial layer simply doesn't appear.

**Example:** Daily Brief's editor's note on an iPhone 12 (no Apple Intelligence) or on a Hindi-locale device (unsupported language). The editor's note section vanishes; the Calendar / Reminders / Birthdays tabs below continue showing the underlying events and reminders directly.

**When to use:** the FM output is editorial commentary on data the user already accesses through some other surface in the same view. This is the most common case for FM features in From Ink — the data layer (EventKit, SwiftData, etc.) is already presented somewhere; FM adds prose on top of it. This is the case §5's hide-rather-than-fake rule covers.

### 6.2 Disable with messaging (for FM-essential surfaces)

The feature shows a localized "not available in this language" surface in place of its normal UI. The user understands the limitation; the feature is honest about it.

**Example (hypothetical):** an "AI summarize this notebook" button on the library screen. The summary is the *only* surface presenting that information — there's no separate "all my notebooks' contents" view the user could fall back to. On an unsupported locale the button shows a disabled state with `AppStrings.Library.summarizeUnavailable` ("Summarize isn't available in Catalan yet.").

**When to use:** the feature's value is FM-essential AND there's no separate data surface that already conveys the same information. The feature is prominent enough that silently hiding it would confuse the user.

### 6.3 Hide entirely

The feature does not appear in the UI at all for users whose locale is unsupported.

**When to use:** the feature is FM-essential AND non-critical (an "extra" rather than a core surface) AND its absence does not confuse the user. Use sparingly — hiding can feel arbitrary if the user discovered the feature on a different device and now expects it.

### Decision matrix

| Property | Choose |
|---|---|
| FM wraps/comments on data already shown elsewhere in the same view | §6.1 Hide the FM surface |
| FM-essential, no separate data surface, prominent | §6.2 Disable with messaging |
| FM-essential, no separate data surface, non-critical | §6.3 Hide entirely |

Every FM-gated feature must declare its gating choice in its own EDD or feature-level comment, alongside a `supportsLocale`-style check at the entry point.

### Where the check lives

The runtime check happens at the **feature boundary** — typically the wiring view or reducer. It checks both:

1. `foundationModels.isAvailable()` — the framework is present on this device.
2. `foundationModels.supportsLocale(cal.userLocale())` — the model can produce output in this language.

Both must be true to expose the FM path. Either being false routes to the chosen gating policy.

## 7. String localization (the AppStrings pattern)

All chrome strings flow through `AppStrings.{Domain}.{key}` static lets or functions, which wrap `NSLocalizedString` with explicit `value` and `comment` parameters. The full rule is in `CLAUDE.md`; this section is the localization-specific addendum.

**Plurals.** Use `String.localizedStringWithFormat` with a `.stringsdict` file for any string whose form depends on a numeric count. Example: `home.briefFallback.reminderWithMore` carries `value: "Don't forget %1$@ — plus %2$d other reminders."` — translators add a `.stringsdict` entry to handle their language's plural forms (e.g., Russian's 3 forms, Arabic's 6).

**Reordering.** Format strings use positional placeholders (`%1$@`, `%2$@`) so translators can reorder. The English `"%1$@ at %2$@"` becomes Japanese `"%2$@に%1$@"` (time before event, particle marker) without code changes.

**List joining.** Use `ListFormatter` keyed to the user's locale, never a hard-coded `joined(separator: ", ")`. English picks up the Oxford comma + "and"; French uses "et"; CJK uses `「、」`; Arabic uses an Arabic comma.

**Authored content.** Event titles, reminder names, notebook titles, page text — never pass through `NSLocalizedString`. The user typed them; we respect their language choice.

## 8. Date + Calendar + Locale pattern

This pattern is fully specified in `dates_edd.md`. Summary for this EDD:

- Inject `CalendarContext` as the canonical source of `now`, `userLocale`, `userCalendar`, `userTimeZone`.
- Every component view that renders a date or weekday takes `Date` / `Calendar` / `Locale` / `today` in its Model init and derives display strings internally.
- No bare `Date()`, no `Locale.current`, no `Calendar.current` in feature code. The exceptions live in `CalendarContext.liveValue`.
- Day-keys for SwiftData predicates use the Gregorian / POSIX `yyyy-MM-dd` format from `CalendarContext.dayKey(_:)`, regardless of the user's preferred calendar. The day-key is for the database; the rendered date is for the user.

## 9. Numbering systems

Digits beyond ASCII 0-9 are first-class. Common targets the architecture must handle:

| System | Locale identifier override | Example: "9:00" |
|---|---|---|
| Latin (default) | (none) | 9:00 |
| Arabic-Indic | `@numbers=arab` | ٩:٠٠ |
| Devanagari | `@numbers=deva` | ९:०० |
| Thai | `@numbers=thai` | ๙:๐๐ |
| Chinese Hanidec | `@numbers=hanidec` | 九:〇〇 (rare in practice) |

`Date.formatted(.dateTime.hour().minute().locale(cal.userLocale()))` produces correctly-numbered times when the locale has the override applied. Tests use locale identifiers like `Locale(identifier: "hi_IN@numbers=deva")` to lock the numbering system for snapshot determinism — iOS's default `hi_IN` returns Latin digits, so tests would silently pass with the wrong system without the explicit override.

Integer formatting in code uses `Int.formatted(.number.locale(locale))`. String interpolation (`"\(count) items"`) bypasses locale numbering — always go through the formatter.

## 10. Layout direction

Right-to-left languages (Arabic, Hebrew, Persian, Urdu) flip the entire reading flow. Discipline:

- **SF Symbols.** Use direction-aware symbols (`arrow.backward` / `arrow.forward`, `chevron.backward` / `chevron.forward`) for "previous/next" semantics. The fixed-compass symbols (`arrow.left`, `arrow.right`) are for actual directional intent only — and almost never appropriate. The full rule lives in `feedback_directional_sf_symbols.md`.
- **Custom layout.** Anything you build with explicit `leading` / `trailing` (SwiftUI HStack, Layout containers) honors layout direction automatically. Hard-coded `.left` / `.right` does not. Default to leading/trailing.
- **Text alignment.** SwiftUI's `multilineTextAlignment(.leading)` flips per-locale; `.left` does not.
- **Numerals in RTL.** Numerals in Arabic/Hebrew flow left-to-right *inside* the right-to-left line. The OS handles this automatically; do not manually reverse strings.
- **Date intervals.** `Date.FormatStyle` interval and relative formatters produce correctly-flowed output. `RelativeDateTimeFormatter` likewise — already used in `HomeWiringView.relativeFormatter`.
- **Custom drawables.** Any view that draws content imperatively (PaperKit canvas, custom Shapes) must honor `@Environment(\.layoutDirection)` when its content has a leading/trailing concept.

## 11. Testing strategy

### 11.1 Per-language test fixtures

The hide-rather-than-fake rule (§5) shrinks the test obligation surface significantly. Per FM-gated feature, ship at minimum:

- A unit test for the **hide path** — assert that when the FM service returns empty (simulated unavailable, or unsupported locale), the model resolves to "section omitted" state. For Daily Brief this means `HomeDailyBrief.Model.showsEditorsNote == false` when `editorsNote.paragraphs.isEmpty`.
- A unit test for the **happy path** — assert that when FM returns content, the editor's note renders.
- A snapshot test rendering the visible chrome (tabs, masthead, etc.) with `Locale(identifier:)` + `Calendar(identifier:)` + `TimeZone(identifier:)` triples covering RTL, non-Latin digits, and non-Gregorian calendars. The chrome localizes via `AppStrings`; that's what needs per-language coverage.

Existing examples:

- `DailyBriefRetentionTests` — exercises the retention helpers against an in-memory `ModelContainer`. Pattern is reusable for testing FM-empty / FM-loaded state resolution.
- The `feedback_snapshot_test_frame.md` memory entry pins the HStack-frame requirement for snapshot tests of localized components.

### 11.2 Locale + TimeZone are always explicit in tests

Tests never depend on `Locale.autoupdatingCurrent` or `TimeZone.current` — both vary by host. Lock fixtures explicitly:

```swift
let calendarContext = CalendarContext.fixed(
    now: ...,
    locale: Locale(identifier: "hi_IN@numbers=deva"),
    timeZone: TimeZone(identifier: "Asia/Kolkata")!,
    calendar: Calendar(identifier: .gregorian)
)
```

### 11.3 Test obligations per feature

When adding an FM-gated feature, the PR must include:

1. **Hide-path tests:** with FM unavailable, the FM-generated surface omits itself cleanly (no empty box, no stub text, no English mixed into a non-English UI). For data-wrapper features (§6.1), assert the underlying data surface still renders unchanged.
2. **Gating tests:** with FM available + locale supported (happy path); with FM unavailable on the device; with FM available but locale unsupported via `supportsLocale`.
3. **Chrome snapshot tests:** any localized view component the feature touches (tab strip, masthead, etc.) snapshot-tested with locale fixtures covering at least one RTL, one non-Latin script, and one non-Gregorian calendar from the target list.

A PR landing an FM feature without these isn't reviewable.

## 12. Migration plan

The project ships with English as the development language. Localization rollout:

### Phase 0 — Foundation (now)

- Every team-authored user-facing string already routes through `AppStrings` per `CLAUDE.md`.
- Deterministic fallbacks exist for FM-gated features (currently: Daily Brief).
- `CalendarContext` is the canonical locale/date source.
- This EDD exists; the language list (§3) is TBD.

### Phase 1 — Pilot a single non-English language

- Ratify the target language list (§3).
- Pick one **non-English, FM-supported** language for the first translation pass — likely Spanish (largest secondary market and shares Latin script). This lets us validate the chrome translation flow without also debugging RTL / non-Latin script / fallback issues.
- Add the language to `knownRegions` and ship a Spanish `.strings` file.
- Run the full test suite with Spanish fixtures. Fix gaps.
- TestFlight with Spanish-locale testers.

### Phase 2 — Add FM-supported languages

- Roll out remaining FM-supported target languages (Japanese, German, French, Italian, Chinese-Simplified, Portuguese-BR, Korean as applicable).
- Per language: translation pass → fixture tests → TestFlight.

### Phase 3 — Add FM-unsupported languages

- For each target language Apple FM does **not** support, FM-gated surfaces simply do not appear per §5. The user sees the underlying data surfaces (tabs, lists, detail views) in their language; the editorial layer is absent.
- The translation burden is bounded by chrome — `AppStrings` keys for app structure, button labels, accessibility hints, etc. No "FM-equivalent prose in N languages" obligation exists.
- This is where RTL, non-Latin script, and non-Gregorian calendar testing earns its keep. The architectural investment from `dates_edd.md` and the locale-aware components ensures the data surfaces themselves are correct in every target language.

### Phase 4 — Ongoing maintenance

- When Apple expands FM language coverage, no code change required — the `supportsLocale` check picks up the new languages automatically. Translation work (if any) is the only follow-up.
- When the team adds a target language, run the same per-language test obligations from §11.3 against existing features.

| # | Question | Impact |
|---|---|---|
